### B. Non-applicability and exceptions

A coordinator may propose that one activity is not applicable,
but only the explicitly authorized mission approver may accept it. Record the
activity, concrete reason, scope/agreement basis, proposing actor, approving actor, exact Version and server time. A contractual scope change additionally preserves the actual agreement of the parties; internal approval alone cannot erase an undertaking. A pending/rejected request changes no obligation. Approval is a
visible exclusion, never fulfilled work or an implicit Contract amendment.

An activity that is still due stays required/blocked, with a responsible person,
next action and due date; a delay is not non-applicability. Cancelling a Task,
removing a Document or clearing a result never grants an exception. Restoring
applicability appends a new attributed decision and can block completion again.
No general waiver allowing completion with still-unfulfilled required work is
proposed. Contractual scope changes need their own valid recorded authority;
this UI cannot manufacture agreement by the parties.

The known first-tenant principal approver is Iurie through explicit
application assignments; technical access and Project responsibility are not
delegation. No real grant is created by this decision.

## 5. Concepts, states and corrections

These are proposed terms, not additions to the approved glossary yet.

- **Mission policy adoption:** an immutable link from an existing exact copied
  plan and its thirteen Task identities to one identified obligation policy
  Version. No Project, Task, result, source row or Contract is recreated/rewritten.
- **Activity applicability:** required initially; an approved non-applicability
  decision excludes that row from required work while keeping it visible.
- **Activity readiness:** open work, required Task cancelled, missing result,
  result/evidence unavailable, submitted result, or approved exclusion. Submitted
  is not verified or automatically accepted. Loss of read authority is unavailable,
  not missing, and cannot disclose the protected reason or metadata.
- **Mission completion basis:** the immutable actor/time, policy/source/Task
  identities, observed applicability decisions and exact result/PDF references
  reviewed by the closer, with consulting/handover declarations and their basis.

Only an open Project with the complete recognized thirteen-row snapshot may
adopt the policy; closed Projects cannot be retrofitted. Existing v1 plans remain
readable and usable without adoption. Later adoption cannot be undone to evade
completion guards; changing a policy or required scope uses a separately approved
version/decision path, never an in-place edit. Unknown/missing mapping refuses
adoption. Task title edits, extra Tasks, result correction or Document succession
never change the source mapping automatically.

An exclusion proposal has pending/approved/rejected states against its observed
applicability revision. Decisions are immutable. Reclassification records a new
reasoned decision with a predecessor; concurrent or stale decisions conflict.
A result correction or Task reopening before closure invalidates readiness for
the observed set; the closer must reload/review the new set. Extra Tasks retain
the ordinary no-open-Task completion gate but do not become source obligations.

Project lifecycle still owns activate/hold/resume/complete/cancel. Governance adds
a completion precondition only to adopted missions; it changes no lifecycle
status or stage. Cancellation remains a different, reasoned terminal outcome
under the ordinary no-open-Task gate, retaining unfulfilled obligations visibly.
It never records successful mission completion. Closed Projects stay terminal;
historical reopening means viewing the dossier, not resuming execution.

## 6. Commands, history and invariants

Commands carry observed policy/adoption/applicability/lifecycle and consumed
Task/result revisions, a stable actor/Workspace idempotency key and only the
explicit intent. The server establishes actor, time, scope and exact references.
Client booleans or counts cannot attest fulfillment. Bounds, normalization and
closed payload shapes follow the existing command discipline and are fixed in
each implementation issue; no caller-selected SQL, rule language or arbitrary
workflow graph is accepted.

Use the original Client/relationship and Project serialization order. Completion
rechecks the entire exact obligation set, current authority and no-open-Task gate
in the same transaction as lifecycle change, immutable reviewed snapshot, receipt,
minimal Activity event and Client operational-use fence. Every existing completion
entry point must enforce adoption; no legacy endpoint bypass is permitted.

Completion versus Task reopen/cancel/edit, result correction, policy decision,
consumed Document qualification/authority change, access revocation, Client
archive/union and competing lifecycle change must have one serializable outcome. A changed evidence set refuses the
stale confirmation, rather than reviewing whatever is latest at commit time.
An unrelated field change or a later official designation does not invalidate an
unchanged eligible historical PDF reference or add authority it did not consume.
No failed command leaves a partial approval, lifecycle change, receipt or event.
The database independently constrains scoped references, unique adoption,
immutable decisions and coupled completion evidence. PostgreSQL defense does not
replace authorization or human review.

Exact retries recheck live consumed authority and target visibility, then return
the conserved receipt before rejecting its old observed revision. Changed-key
reuse conflicts. Replays do not duplicate history, Project/Task records or events.
An earlier read cannot replace confirmed completion; uncertainty conserves the
same intent/key. Missing capability or exact-scope changes retire only the
affected protected intent, preserving independent result/PDF/navigation owners.

Activity Log owns attributable adoption, applicability decisions, next-action
changes and reviewed closure. Event metadata stays minimal; reasons, declarations
and PDF identities remain in their separately authorized owning records. No
customer prose, evidence bytes or inaccessible Company identity enters generic
Activity metadata.
