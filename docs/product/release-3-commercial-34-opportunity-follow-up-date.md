## 34.2 Problem, value and complete journey

A user can preserve a next-action sentence but cannot deliberately record a separate planning date, explain its correction or find authorized cases through a chosen date. The outcome is edit → conserved reload/history → deliberate bounded discovery → exact Request detail. Value is demonstrated by finding the intended cases and reconstructing their date changes without changing another commercial fact; no delivery-speed or overdue metric is inferred.

1. As a reader, I distinguish no declaration, an explicit undated declaration and a literal date, with attribution and complete accessible history.
2. As an authorized updater, I set, correct, clear or confirm the date with the required reason and recover safely from stale or uncertain work.
3. As a planner, I choose a through date, continue the authorized bounded results and open the exact native Request detail.
4. As an administrator, I explicitly grant/revoke the independent bundle without widening an old capture.
5. As a user changing context, authority or native outcome, I cannot accidentally submit or recover retired work.

## 34.3 Owned fact, absence and native outcome epoch

One Opportunity has one independent follow-up head. It never changes the Request, next-action text, responsible actor, native outcome, Sales Stage, Client reference, Offer, Contract, Project or Task. Changes to text/responsibility/stage never retarget, clear or reconfirm the recorded marker. Old commands, DTOs, fingerprints, receipts, Opportunity.version and last-mutation attribution retain their meaning; date writes have their own revision.

| State                                             | Meaning                                                                          |
| ------------------------------------------------- | -------------------------------------------------------------------------------- |
| `UNRECORDED`, revision 0                          | No declaration. No date, confirmation, attribution or fabricated history exists. |
| `RECORDED`, revision ≥1, `followUpOn: null`       | A deliberate undated declaration, distinguishable from legacy absence.           |
| `RECORDED`, revision ≥1, `followUpOn: YYYY-MM-DD` | A deliberate literal calendar date, with its recorded native outcome epoch.      |

Dates use exactly ten ASCII characters, real Gregorian calendar days, years `0001`–`9999`; reject impossible days, timestamps, whitespace, alternate forms and coercion. Store/compare the literal date without timezone or instant conversion. No browser/server clock, locale, capture date, text extraction or migration supplies a default.

The **native outcome epoch** is an opaque server-established identity of the latest material §23 transition, scoped to the original Opportunity; initial `OPEN` has its own identity grounded in that Opportunity's creation. The immutable native transition identity establishes each later epoch, including Hold, Resume, Win, Lose, Disqualify, Archive and Reopen. It is not a browser value, date-write counter, new historical backfill, current native version or guessed wall-clock timestamp. Text, reassignment and stage mutations do not change the epoch. Existing outcome commands and their receipts are unchanged; derive the epoch from conserved native identity/history. Missing or contradictory native transition evidence fails closed; never treat it as initial `OPEN` or fabricate an epoch.

Every fresh declaration/change/clear/confirmation requires currently `OPEN`. Raw current/history remain readable under live read rights in all six §23 statuses. Only an `OPEN`, dated head explicitly confirmed for the current native epoch is eligible for discovery. A material outcome transition leaves the recorded head intact but invalidates that confirmation. Resume/Reopen never revive it automatically. A deliberate new confirmation while `OPEN` records the current epoch, increments the own revision and requires a reason, even when the date is unchanged. Clearing/null may likewise be confirmed; it never enters dated discovery.

## 34.5 Closed command, no-op, receipts and races

Use a separate native Opportunity follow-up command; do not extend the old next-action body. The target is the original Opportunity identifier. The body contains **exactly** `expectedRevision` (nonnegative safe integer), `observedOpportunityVersion` (positive safe integer), `followUpOn` (literal date or explicit null) and `reason` (explicit null or valid text). No field is optional. Use the existing idempotency-key validation convention, in a separate Workspace/Company/acting-membership command namespace.

First declaration may have null reason. Every later **material** change, clear or epoch confirmation requires a literal nonblank reason, at most 500 UTF-16 code units. Any supplied reason must meet that rule, including on a no-op; preserve whitespace and Unicode exactly, reject malformed Unicode and NUL, and never trim, normalize or coerce. Omitting either field is invalid; explicit null follows the declaration/reason rules above, while an empty reason is invalid.

Apply this deterministic order inside the authorized transaction:

1. Validate the closed body/key and current complete actor/capture/target-read prerequisites. Unknown/foreign/hidden target uses the native safe not-found boundary.
2. Resolve a previously committed key. Its exact fingerprint includes target, original scope/actor, all four fields and their literal values. Exact replay returns the stored past receipt after live authority revalidation, **before** fresh-write revision/native-version/`OPEN` checks. Different intent with that key returns `409 IDEMPOTENCY_CONFLICT`.
3. For a new key, lock/revalidate the native Opportunity and own head in a consistent order with §23 and Access. Require both observed versions to match and native status `OPEN`; otherwise return safe `409 STALE_FOLLOW_UP`, `409 STALE_VERSION` or `409 OPPORTUNITY_NOT_OPEN`, without partial persistence. Both observed values come from a current read, never from a receipt.
4. Compare literal `followUpOn` and server current outcome epoch with the head. Same value/same epoch is `unchanged`: conserve the revision and fact, store only its durable receipt, and add no history/event. A different reason alone never edits history. First explicit null is material; same value/new epoch is material. Validate a required material reason before committing.
5. A material result increments the own revision exactly once and records before/after fact, reason, actor membership with captured display label, server time, receipt and private event atomically, including successful response construction. It changes no native Opportunity version or last-mutation fields.

Equal simultaneous keys converge to one receipt; same key/different intent conflicts. Different keys at one expected own revision permit at most one material winner; a later stale equal-value attempt conflicts before no-op comparison. A fresh no-op requires current versions/`OPEN` just like any new command. Serialize date versus native outcome and authority transitions: either the date commits first and the later outcome invalidates eligibility, or outcome/revocation commits first and the fresh date is refused. Native text/stage/reassignment racing first makes the observed native version stale without changing the existing recorded marker.

Receipt format `opportunity-follow-up.v1` is closed and immutable: format, Opportunity identifier, `outcome: updated | unchanged`, and the complete resulting recorded fact at its resulting own revision. Its fact contains `followUpOn`, confirmed epoch, original recording attribution/time; no-op retains that prior attribution. A past receipt is not current state and cannot reactivate discovery. Store the complete literal intent and receipt under their supported closed version; reject unknown formats, missing/extra fields or inconsistent material/no-op facts rather than silently discarding stored information.

## 34.6 Native integrity, private history and events

The own head, immutable history and receipt are bound to the same original Workspace/Company/Opportunity by native constraints. Material history preserves the complete before state (`UNRECORDED` or recorded revision/date/epoch/attribution) and after recorded state, literal reason, command linkage, server actor/time and contiguous revision. Recorded heads never revert to `UNRECORDED`; correction/clear is another entry. No history edit/delete or arbitrary effective date exists.

Native coupled integrity must reject cross-scope references, unknown formats, forged/missing history/receipt/event, extra or inconsistent before/after fields, a head ahead/behind its chain, mismatched no-op/material outcome, contradictory actor/time/epoch, duplicate material revision and partial direct persistence. A structurally valid but fully fabricated coupled fact must also fail without the authorized native mutation path; matching foreign keys alone is insufficient. Failures in event recording, receipt storage, response construction or commit roll back the complete transaction. Do not repair corruption by inventing history.

Each material command records exactly one private `opportunity.follow_up.updated`, targeting the original Opportunity with server actor/time and exactly `{ revision }` metadata. Dates, reasons, keys, fingerprints and actor labels stay out of event metadata and diagnostics. Reads, rejected/failed/stale commands, no-ops and exact replay emit none.

Exclude the new private event family and date facts from generic Activity, commercial Activity, Home, global search, filters/counts and export **before** selection/pagination/counting, including for all-grants readers; no target/existence or short-page side channel. Native current/history use §34.4 only. Separate `company_opportunity_follow_up_coordinator_assignment.granted` / `.revoked` retain existing Company assignment administration visibility, actor/time, `company_role_assignment` target and bundle-label-only metadata; exactly one per actual state change, none for repeats, failure or exact replay. Only those safe administration labels enter generic administration views.

## 34.7 Current reads, history and deliberate discovery

The existing Request detail remains the entry point; fetch the protected follow-up subresource only under §34.4. Its current read returns original Opportunity identity, native status/version/current epoch, the discriminated own head and the first history page. No-entry returns revision 0 and an empty history, not a fabricated recorded-null fact. Display recorded actor label/server time and confirmation state exactly; another user's visibility of the native Request alone exposes no date/history.

Own history is newest own revision first, at most 25 entries per page, each with complete immutable before/after/reason/attribution under the same closed `opportunity-follow-up.v1` format. The first page supplies an observed `headRevision`; continuation carries that same head and an opaque position bound to the original Workspace/Company/Opportunity, requesting actor and consumed read captures. Revalidate live rights and head on every page; a changed own head returns `409 FOLLOW_UP_HISTORY_CHANGED` with no partial rows and requires deliberate reload. Empty/no-entry and fully exhausted histories have no cursor. History reads change no state. No history count is exposed.

Discovery lives in the existing Company commercial workspace. Require a deliberate scalar `through=YYYY-MM-DD`; no omitted/empty/repeated boundary or clock-derived default. Select only current eligible heads (§34.3) with `followUpOn <= through`, inside one active Company and current complete read authority, ordered by literal date ascending then Opportunity UUID ascending. Return at most 25 rows with date, original Opportunity/Request identifiers, authorized native title and confirmation attribution, plus only the existing permission-filtered optional Client projection needed to open that Request. No reason, hidden Client data, total, cross-Company view, overdue/today/SLA claim, ranking or automatic polling.

An opaque cursor, at most 2,048 characters (also the history cursor limit), binds its validated format, position, requesting actor/Workspace/Company, consumed capture identities/versions and unchanged through boundary. Apply authority/status/epoch/date predicates **before** bounded rows, lookahead and cursor creation; a hidden row never creates a visible continuation. Use at most one extra eligible row to decide continuation. Both reads accept only their stated scalar query fields; unknown, repeated or non-scalar fields fail validation. Reject malformed, repeated, foreign-scope/capture or altered-boundary continuation safely; never accept a client cursor as authority. Each page is a fresh observation: intervening date/outcome changes can alter membership, so there is no frozen global membership guarantee. Returned positions advance strictly; a repeated/nonadvancing continuation fails safely and offers a deliberate restart rather than an infinite loop.

## 34.8 App lifetimes, failure and recovery

Use the current Prisme Request detail and Company commercial workspace; no new global shell section or raw-identifier form. Keep Company context visible and share the native one-open-Opportunity-editor rule. Show no declaration, recorded undated, recorded date, stale confirmation, history/loading/exhausted, read-only, closed/held, empty discovery and error states distinctly. Setting/clearing/confirming is explicit; opening a date control or entering a through boundary writes nothing. A changed discovery boundary retires its loaded pages/cursors while preserving unrelated valid native detail and work.

The new owner uses monotonic lifetimes for actor/session, Workspace/membership/Company, consumed captures, selected Request/Opportunity, native outcome epoch, command, history head and discovery boundary/continuation. Context/capture/native-outcome invalidation irreversibly retires its current edit, pending/uncertain attempt and late replies; A→B→A and equal-permission replacement never recover retired work. A current native non-outcome version conflict requires reload/review of the date attempt. Unrelated native editors keep their own established rules; a date-only invalidation does not discard unrelated valid commercial work.

An older full-Actor recovery response cannot overwrite a newer actor, capture or context observation. Generation-check success, failure and cleanup callbacks before installation; abort alone is insufficient. One command owner survives ordinary re-render/locale changes but not retirement. While a command is pending/uncertain, disable conflicting date actions. An uncertain outcome retains the exact original input/body/key only in transient memory within its current live owner and permits only explicit identical retry under that still-valid lifetime. Editing or adopting newer state requires explicit review and a new intent/key. A confirmed successful receipt followed by read-refresh failure remains confirmed: offer a read retry, never relabel it uncertain or silently submit it again. A receipt may show a past result while a fresh read shows later state.

Keep this journey's follow-up business payload (dates, reasons, identifiers, cursors, receipts, command input/bodies/keys and history) out of browser navigation URLs (path/query/hash), browser storage (including localStorage, sessionStorage and IndexedDB), service-worker/Cache API caches, analytics and diagnostics. Established locale/Company-selection preferences retain their existing owning rules and carry no follow-up payload. The explicitly authorized API identifier, `through` and cursor transport remains allowed; an API request URL is not a browser navigation URL and must not become a persisted navigation payload or literal diagnostic log. Cold reload/remount may recover only fresh authorized server reads, never restore a prior draft, uncertain body/key or retired owner from browser persistence. Ordinary locale changes preserve work only within the still-live transient owner.

Missing identity returns `401`; lost prerequisites/invalid Company return safe `403`; unknown/inaccessible/foreign targets share native not-found. Invalid fields return field validation without persistence. Stale version/history, changed key or non-`OPEN` conflict prompts deliberate reload and review, preserving a still-authorized edit/uncertain body until that explicit choice; invalidation retires it immediately. Provider/network/persistence failures expose safe retry status without literal private content. Malformed/unknown response or stored format fails closed and is never installed as success. Diagnostics use safe correlation identifiers only.

All product copy/errors/accessible labels are localized in `ro`, `ru`, `fr`, `en`; reasons and captured labels remain literal business content. Show locale-appropriate dates without changing the calendar value/order. Preserve input across locale changes. Require semantic controls, keyboard operation, visible focus, error association and recoverable focus after save/conflict/continuation, with actual desktop and narrow layouts under the UX owner.
