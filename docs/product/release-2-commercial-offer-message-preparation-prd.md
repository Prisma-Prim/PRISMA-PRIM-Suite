## 1. Purpose and source classification

A user who can already read a supported exact Offer Version can prepare a manual provider-free message, review its intended source and recipient, explicitly copy its text and deliberately obtain the exact non-official PDF for manual attachment outside the application. The application never sends, marks attached/sent/accepted or records a transmission.

This capability inherits the [Product Vision](product-vision-prd.md), [decision record §11.4 / DEC-057–060](consolidated-product-decision-record.md#114-gmail-risk-boundary), [Offer §§18.6/18.8](release-3-commercial-18-offers.md#186-permissions-and-approval), [exact PDF §33](release-3-commercial-33-non-official-pdf-download.md), [Authorization](tenant-company-client-authorization-prd.md), [Activity](activity-log-accountability-prd.md), [Platform](platform-security-reliability-operations-prd.md), [UX](ux-localization-configuration-prd.md), [CONTEXT](../../CONTEXT.md) and ADRs [0003](../adr/0003-nestjs-owns-business-decisions.md), [0006](../adr/0006-workspace-tenancy-and-company-scoped-authorization.md) and [0008](../adr/0008-bounded-document-content-storage.md). Those owners retain their rules; this document owns only their preparation consequences.

## 2. Complete outcome and value

Native current/history Offer selection → prepare one manual recipient/subject/plain body → inspect original exact source, recorded party, non-official meaning and current actor → explicitly review → copy the intended fields and separately offer the verified exact PDF download. Value is demonstrated by completing that synthetic journey without a hidden spreadsheet, source retarget, business mutation, unauthorized disclosure or guessed external result. No adoption/time-saving percentage or delivery claim is inferred.

1. A reader opens the intended current or historical Offer rather than entering IDs.
2. The reader writes the recipient, subject and message; the application invents none of them.
3. The reader checks the copied source/party and current working actor, then deliberately confirms review.
4. The reader explicitly copies recipient, subject or body and downloads the intended exact PDF for manual use.
5. The reader understands clipboard offered/failed, download offered/failed and that no file was attached or message sent by PRISMA.
6. A user changing scope, consumed authority or exact target cannot revive or publish an old draft/reply.

## 3. Exact source and authority

The first source is one currently readable exact Offer Version in either already delivered PDF tuple:

- `COMPANY_MODEL_ESTIMATE`, `NON_OFFICIAL_REHEARSAL`, `OFFER_COMPANY_CONSULTING_RO` renderer v1, `INTEGRATED_MANAGEMENT_CONSULTING_RO`, `ro`, retaining its literal illustrative/company-supplied provenance;
- `ILLUSTRATIVE`, `OFFER_ILLUSTRATIVE` Template v1, all immutable Snapshot lines unadjusted, `en`, exactly as§33.13.

Keep the complete Offer root, Workspace, Company, Opportunity, Version, provenance, renderer, language and source HTML digest binding. Current-head identity is never substituted; changing head/model or current party data does not rewrite a still-readable selected historical Version. Other tuples remain unsupported, with existing source consultation independent of composer availability. Source content is never caller-supplied HTML or regenerated from current data. This first capability adds no Contract support simply because the PDF owner also supports it.

**Selected read-derived authority:** preparing/copying this ephemeral manual text is a read-derived convenience for the already authorized exact Offer reader, with current active identity/member/Company/context and owning native Opportunity visibility. It grants no new sending, approval, Offer preparation, transmission, Client, Contact, model, economic or Document permission. Native exact PDF download keeps precisely its independent current intersection and final check. No new permission bundle, old-capture expansion, migration or real assignment is introduced.

Display only data already allowed by that owning read: exact reference/Version, copied party/source meaning and current working actor. Existing live Client projection remains permission filtered. Manual recipient entry neither identifies a stored Contact nor verifies ownership, affiliation or legal authority. Native Contact lookup/import is excluded. Responsibility, Director title and old successful reads grant nothing.

Access must supply a narrow way to bind the new owner's consumed context/intake/Offer capture identities/versions, without depending on Date or Finance grants and without querying Access tables inside the message module. A read-only protected preparation observation, if needed, returns only authorized source identity/capture information, never body/recipient persistence. Its exact DTO/routes are technical assignment choices. Current source lacks a general R2C context-capture projection, so this fit must be closed before delegation. Do not silently broaden/refactor existing PDF authorization or claim its current effective-permission-only scope proves the new owner's lifetime.

## 4. Manual field grammar

All fields start empty. Opening the form, reading a Version or locale choice supplies no recipient, subject, prose, real address, tariff or legal clause. No AI or provider is called.

| Field     | Exact supported input                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Recipient | One literal ASCII mailbox, total 1–254 characters; local part 1–64 characters using dot-separated nonempty atoms of ASCII letters/digits and `!#$%&'*+-/=?^_`, backtick, left/right brace, vertical bar and tilde. No leading/trailing/consecutive dot. Domain has at least two dot-separated nonempty 1–63-character ASCII labels with letters/digits and internal hyphens, beginning/ending alphanumeric. No display-name form, quoted local part, whitespace, commas/semicolons, CR/LF, C0/C1, Unicode/EAI or coercion. Preserve case; make no DNS, deliverability, organization or consent claim. |
| Subject   | Literal nonblank 1–200 UTF-16 code units, valid Unicode, no NUL/C0/C1 or line breaks; preserve valid whitespace/case.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Body      | Literal nonblank 1–10,000 UTF-16 code units, valid Unicode, no NUL/C1 or C0 except TAB/CR/LF; preserve line breaks/whitespace/case, no markup interpretation or automatic translation.                                                                                                                                                                                                                                                                                                                                                                                                                |

These are selected support bounds for the first copy-only UI, not recovered business requirements or a full SMTP/RFC address validator. Invalid fields produce localized field errors without external effects. Partial entry remains editable in a still-live owner. No normalization, transliteration, trimming, address guessing, auto-completion from Client data or inferred communication language occurs. A future broader grammar/template support needs its own decided contract.

The intended attachment is not another form field: exactly one server-established selected Offer/PDF tuple. Its safe filename/byte metadata come only from the native download owner. The user cannot supply a URL, arbitrary file, representation checksum, Attachment ID or paste a source identifier. The copied message body contains exactly the human's body; the application appends no clause, approval, source citation, recipient or signature automatically.

## 5. Review and export boundaries

The composer shows selected internal reference/Version, source language/provenance, copied party, current working actor and the preserved non-official/rehearsal meaning outside the literal body. Exact source viewing uses the native Offer owner. Show the existing recorded decision/response state truthfully without changing the frozen document or implying permission to send it.

Require an explicit transient review confirmation after valid fields and exact source are visible. This means the user reviewed recipient/text/intended source for this preparation, not internal business approval, verified mandate, Iurie consent, actual sending or acceptance. A change of field or source invalidates that confirmation. A locale-only re-render preserves literal text and current review inside the live owner. No review receipt/history/event is stored.

After review, separate buttons copy **recipient**, **subject** or **body** as plain text. Their labels name exactly the field copied. No generated RFC message, hidden header, HTML, combined clipboard packet, clipboard read or automatic fallback write exists. Each explicit copy captures the exact reviewed field/target/owner generation, revalidates current complete native source authority through its server owner, and compares its exact consumed captures and source binding. Immediately before invoking the clipboard, fence again against actor/context/capture/target/edit/review/operation retirement. A field edit invalidates review and retires an outstanding copy observation; its late authorization reply cannot copy either the old or new text. Prevent duplicate dispatch while that copy action is pending.

Compose this live revalidation with clipboard user-gesture constraints honestly: if browser activation/permission prevents copying after the protected read, show failure/manual selection instead of bypassing it. Do not request broad clipboard-read capability or retry on a timer. A semantic selectable field/manual-copy recovery is allowed after deliberate user action within the still-live authorized owner; it does not claim success.

Explicit clipboard invocation and native PDF offering are the intended user-selected output boundaries. The application can suppress a not-yet-invoked stale action and late success/failure/focus/cleanup feedback; it cannot retract an OS clipboard write after handing its argument to the browser, a browser-offered download or saved external bytes. In particular, retirement during an unresolved clipboard promise is not promised to cancel its eventual OS effect. A resolved live clipboard operation reports only that the browser accepted that field, not that it was pasted/read/delivered. A rejected/unknown clipboard outcome reports failure/unconfirmed status and permits a fresh explicit attempt; it creates no uncertain business command or idempotency key. Never clear/overwrite the user's previous clipboard automatically.

Download is a separate deliberate native exact-PDF read with its existing bounded MIME/tuple/digest/actual-parser verification, final server reauthorization, explicit exact retry and Blob cleanup. Completion means **download offered**, never saved/read/attached. The intended attachment remains labeled as intended; no `attached`, `sent`, delivery time or Message ID can be manufactured. If PDF is unavailable or unsupported, retain the authorized draft and expose exact-source recovery; text-copy and PDF outcomes stay distinct.

No `mailto:`, browser navigation payload, open-in-client, external link, Web Share, `.eml` creation or automatic attachment is included in this first selected path. Copy behavior satisfies the provider-neutral copy/open-client alternative without claiming that a mailto URL can attach a browser PDF. Actual mail-client integration would need its own transport/privacy/failure contract.

## 6. Transient lifetime, failure and privacy

One monotonic owner binds authenticated session/identity, original Workspace/member/Company/context, consumed native read assignment identities/versions, original Opportunity/Offer/Version/source digest and review/copy/download operation generation. Effective permissions alone are insufficient. Scope/session/consumed capture loss, replacement at equal permissions, or target change irreversibly retires its draft, review, pending actions and late callbacks. A→B→A never restores it. Current target/source mismatch requires deliberate reload/review of that exact target, never selecting current head silently.

Native unrelated work and its command keys stay independently owned. This read-derived preparation must not remount the entire Commercial workspace, steal mutation keys or reset an independently valid editor/read on unrelated permission changes. Existing navigation arbitration can require deliberate discard before a protected draft's target changes; it must not silently attach an old draft to the next Version. A newer head alone does not invalidate independently authorized preparation for an explicitly selected older immutable Version.

Generation-check token retrieval, native reads, older full-Actor recovery, clipboard completion/failure, PDF/hash/Blob/click/focus and cleanup before installing state. Abort is useful but not the complete proof. A committed sibling business mutation or its failed read-refresh must not become a new R2C uncertain mutation. A current401/403 retires the protected owner and invokes existing scoped recovery, with old full-Actor replies prevented from replacing newer actor/capture/context observations.

Recipient/subject/body/review/source-binding/copy status live only in transient application memory. No new browser URL path/query/hash payload, local/sessionStorage, IndexedDB, Cache API/service-worker caching, analytics, diagnostics, server Drafts, automatic saves or cross-tab restoration. Existing native navigation/locale/Company preferences keep their owning policies and receive no R2C payload. API identifier/hash transport remains allowed under native owners, with no raw literal diagnostic URL logging. A cold remount obtains only fresh protected source data and empty new fields; explicit locale/frame-only changes inside a still-live owner preserve input without duplicate source/PDF/clipboard calls.

Use plain-text rendering throughout. Native authentication/authorization/not-found and exact-PDF safe error contracts remain; never echo hidden IDs, source text or raw provider/parser/clipboard exceptions. No message business event, transmission, approval, response or Registry fact is added. Read-only preparation needs no migration or backfill. The intended zero-write policy must be asserted through real native state/event snapshots, not an Activity label alone.
