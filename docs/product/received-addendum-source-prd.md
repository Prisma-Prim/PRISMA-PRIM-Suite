## 2. Problem, outcome and value

An authorized user can preserve a received copy of an ordinary Company-model
Contract, but cannot truthfully identify a received later Addendum without either
mislabeling it as the parent's own copy or pretending to create a new governed
Contract instrument. The user needs an attributable original and an exact declared
parent association without altering legal or economic facts.

The complete outcome is explicit exact-parent selection → empty confidential
Document → clean preserved PDF → exact current/historical download → deliberate
official Document designation → empty successor → old bytes and relation after
restart. Acceptance measures one conserved registration identity per identical
intent, byte-identical historical downloads, unchanged parent facts and no tested
unauthorized existence/metadata disclosure. No legal-validity or global completion
metric is inferred.

## 3. Scope, actors and stories

One server-validated Workspace and active responsible Company own the Document.
Its original Client Account and the parent's exact recorded receiving-party
discriminator/identity are derived by the Contract owner. There is no All Companies
ownership, Project prerequisite, party inference from prose or canonical-Client
retargeting. A primary party does not acquire an invented additional-entity UUID.
An executed parent remains a recorded human statement, not verified legal effect.

Actors are independently authorized Company registrars, metadata readers, content
readers/uploaders, Version managers, Document approvers and assignment
administrators. A title, named person, preparer, Owner or AI grants none of those
rights. A member may hold multiple explicit native grants; this outcome adds no
separation-of-duties or legal-approval policy.

1. As a registrar, I explicitly choose the received-Addendum family and a labeled
   exact executed parent Version, so that a mutable latest Contract cannot replace it.
2. As a registrar, I see the derived original Client, Company and recorded party,
   so that the received source cannot silently change dossier or legal identity.
3. As a registrar, I state the external source and leave an unknown receipt date
   unknown, so that capture does not invent chronology or signature facts.
4. As an uploader, I preserve a bounded clean PDF and correct a draft through a
   new immutable upload, so that every earlier file survives.
5. As a metadata reader, I distinguish empty draft, official and superseded
   Versions without acquiring protected PDF metadata or bytes.
6. As a content reader, I deliberately reopen an exact current or historical
   upload, including an earlier upload of a draft, after later succession/restart.
7. As a Document approver, I designate a draft holding clean stored content and
   understand that official content does not mean an official/executed Addendum.
8. As a Version manager, I begin an empty successor while preserving the old
   Version, its designation, exact bytes and immutable declared relation.
9. As a reader, I see the declared parent/source only with both endpoint reads;
   independently permitted Document work survives the loss of parent read.
10. As a registrar, I correct only title/purpose and create a distinct Document
    for a wrong association, so that source attribution is never rewritten.
11. As an administrator, I explicitly grant/revoke the separate captured family
    gate, without widening an old assignment or assigning a real person by default.
12. As a user, I retain the exact intent/file/key for an uncertain retry, and
    retry only the read after a confirmed save whose refresh failed.
13. As a user changing locale/frame, I retain literal inputs and correctable
    state without duplicate I/O; replacing identity/scope/relevant authority
    permanently retires older work even if equivalent permissions return.
14. As a historical reader, I reopen conserved evidence after Client/source/model
    changes under the native read boundary without silently moving the original.
15. As an ordinary Contract or generic Activity reader, I learn no source title,
    count, identifier or inferred existence without its independent boundaries.

Included: one immutable `received-addendum` family, fixed
`company-confidential`, native registration/correction/Version/content/history
journeys and narrow exact-parent discovery. Excluded consumers and future
instrument behavior are stated in §§8 and 12.

## 4. Exact parent and closed registration

An eligible parent is an exact ordinary kind `CONTRACT`, origin and Version
provenance `COMPANY_MODEL_OFFER`, in the same Workspace/Company, with an immutable
`APPROVED` decision and `EXECUTED` state backed by its genuine conserved
[§31 reported-signing declaration](release-3-commercial-31-reported-signing-case-acceptance.md).
A bare execution flag or invented declaration is insufficient. Current or
historical exact Versions qualify under that predicate; neither mutable latest
selection nor the same party name substitutes for the exact tuple. Legacy,
Precontract, Addendum-to-Addendum, unsigned, pending/rejected and foreign parents
are ineligible.

New registration uses native Contract/Opportunity read and the original Client's
current native read and active Client–Company/new-use eligibility. Preserve
supported Client-read alternatives, including Workspace `client.manage` where
the Document/Client owner supports it; do not require §31's mutation-specific
recipient-identity-copy permission. No OPEN Opportunity, current source Offer
acceptance/expiry, current model/economic grant, fresh approval, pricing or new
signing declaration is required. The executed parent's frozen facts supply the
context. Later source/Offer/model changes do not retarget an existing source.

Extend the existing Document registration/key protocol with this closed branch:

| Input                                         | Contract                                                                                                  |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `type`                                        | Exactly `received-addendum`; confidentiality is server fixed.                                             |
| `parentContractId`, `parentContractVersionId` | Native valid UUIDs identifying the same exact eligible parent Version.                                    |
| `title`, `purpose`                            | Native trimmed nonempty Document strings, at most 200/2000 UTF-16 code units respectively.                |
| `sourceDescription`                           | Required trimmed nonempty plain text, at most 2000 UTF-16 code units; opaque, unverified declared source. |
| `receivedOn`                                  | Optional or null real Gregorian date `YYYY-MM-DD`, years 0001–9999. Absent/null is not recorded.          |

Text preserves inner whitespace and rejects NUL/invalid Unicode. Reject unknown
keys, invalid calendar dates, malformed/mismatched/foreign identifiers and
unsupported families. The server derives Opportunity, original Client,
Company, receiving party, registering membership/Internal User and server instant.
No browser-supplied ownership/party/amount/model/content/state, external URL,
signature/concordance/acceptance acknowledgment or official reference is accepted.
Do not infer receivedOn from filename, signing date, document date or server time.

Registration atomically preserves the exact parent association, reference/Version
number, recorded original party and declared source/date/actor/time alongside one
Document and Version 1 `draft`, with no PDF or external reference. This is a
declared association, not proof that the file's parties/terms match the parent.
Document relation/source/date/registration attribution are immutable across all
Versions. Native title/purpose correction is allowed only under the existing
draft/revision/history rules; no retarget, type/Client/source/date edit or erase
operation is added. A wrong relation requires another Document.

boundary. Official/superseded content cannot be edited or appended to. A
successor starts empty, copying neither PDF nor external reference. Historical

Archive/delete/discard/retention-policy commands remain outside this family.

## 7. Commands, integrity and conservation

Use the existing actor/Workspace registration-key namespace and native command
receipts. The registration fingerprint contains Company, family, exact parent
tuple and every validated metadata field. Different family, Company, source or
input under the same key conflicts. Before committed registration replay,
revalidate current registration/family and exact native Contract/Opportunity read.
Resolve a conserved identity through its current ordinary Document visibility
before testing fresh Client/parent new-use eligibility. Later readable Client
supersession or source succession cannot duplicate or redirect the original
registration. An unreadable original still denies disclosure.

Other commands consume their own current relevant authority before replay;
post-scan commands recheck it again. They gain no parent-read prerequisite.
Identical replay neither rescans nor changes the current upload, event, Version,
revision or Client fence. An old upload replay cannot restore it over a newer one.
A confirmed command remains confirmed if its response-refresh read fails.

Registration, relation/attribution, initial draft, Client operational-use fence,
durable receipt, final response construction and one native registration event
commit or roll back together. Version/content/correction reuse their native
observed-revision increment and atomic receipt/event/Client-fence protocol.
Join Access, Client, a narrow Contract-owned exact-parent reference and Document
participants in the caller transaction using consistent Access → Client → Contract
reference → Document lock order. No controller reads another owner's private
tables, no nested independent business transaction and no import of the whole
Contract command stack is needed.

Scoped foreign keys/immutable integrity boundaries enforce relation presence iff
this family, exact parent Version/Company/original Client/recorded party binding,
genuine executed declaration and immutable type/relation/source/attribution.
Forged execution flags, coupled invented relations/receipts/events and a correct
Company with the wrong original Client or Version must fail independently of HTTP
validation. Native tests exercise those full coupled attempts, not only omission
of a required child row.

Deterministic races cover same/different registration keys, competing upload/
designation on one revision, harmless source succession, Client archive/union,
source/family/ordinary authority loss in both lock orders, scan versus revocation,
and final event/response failure. Each ordering yields one authorized conserved
outcome or no effects. No wrong relation, bytes, receipt, revision, event, Client
fence or orphan success survives a denied/stale/failed transaction.

Historical original-Client read rules remain native; current corrections/unions
never rebind the source to a canonical Client. Parent content/decisions/references,
execution declaration, economics and Project relationships stay unchanged.
