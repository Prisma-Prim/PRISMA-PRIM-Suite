# Coordinating a shared CI change

**Status:** Approved process, [#1518](https://github.com/Prisma-Prim/PRISMA-PRIM-Suite/issues/1518). [Issue execution](issue-execution.md#ci-and-merge) owns when to apply it.

Use this procedure when a PR changes a shared workflow, lint rule, or test contract that can affect another PR's `quality` result. The shared-change author coordinates the affected PRs and records their disposition in the shared PR. Ordinary PRs keep the usual merge procedure and global strict status checks stay off.

1. **Hold affected PRs before merging the shared change.** List open PRs targeting `main` (`gh pr list --base main --state open --limit 1000`) and compare their changed paths and checks with the new contract. Tell their owners to hold manual merges, disable pending auto-merges (`gh pr merge <pr> --disable-auto`), and confirm the holds (`gh pr view <pr> --json state,autoMergeRequest`). Record the held PRs and recheck for newly affected PRs immediately before the shared merge. If a competing PR merged first, verify the shared PR against the updated `main` and resolve any interaction before merging.
2. **Merge the shared PR and record the shared squash SHA.** Follow the ordinary `quality` and review preconditions. Keep the affected PRs on hold through integration. If an affected PR slips through after the shared merge, check the resulting `main`. If red, follow the red-main procedure in [issue execution](issue-execution.md#ci-and-merge) before releasing other holds.
3. **Refresh affected PRs and verify their integration.** Fetch `origin`, merge `origin/main` into each affected branch with its owner, resolve conflicts and push for fresh PR CI. Read `CI_CHECKOUT` from the successful run's `scope` log (`gh run view --job <scope-job-id> --log`). If `CI_CHECKOUT` is absent, as for documentation-only runs, open the same run's `checks` job log (`gh run view --job <checks-job-id> --log`). In `Check out repository`, find `git log -1 --format=%H` and take the 40-character SHA on the next log line. A missing or ambiguous checkout SHA keeps the hold in place. Inspect that commit's two ordered parents (`gh api 'repos/{owner}/{repo}/git/commits/<checkout-sha>' --jq '.parents[].sha'`). The first parent is the tested base. Check it contains the shared squash SHA with `git merge-base --is-ancestor <shared-sha> <tested-base>` after fetching `origin`. Check the second parent equals the current PR head. Record the head, tested base and successful `quality` run link for each PR. Resume each held PR only after verifying these facts. A failed or missing check, unresolved conflict, or changed head keeps it on hold.

## Example

In [#1400](https://github.com/Prisma-Prim/PRISMA-PRIM-Suite/issues/1400), #1396 passed CI on a base that preceded #1395. Once both merged, the lint rule added by #1395 rejected a new identifier from #1396. Under this procedure, hold #1396 before merging #1395, then verify #1396 on a base containing #1395. That exposes the lint failure while #1396 is still open.
