# Local integration verifier

**Status:** Approved diagnosis procedure

Read this only when diagnosing or reproducing a CI result locally. GitHub CI is the merge gate ([issue execution](issue-execution.md#ci-and-merge)); a local report is diagnosis and never gates a merge. A demonstrated product regression or blocking review finding still needs resolution. Apply the [shared decision procedure](issue-execution.md#shared-decisions-for-major-trade-offs) before a run whose cost is major.

## Scope selection

The command plan and manifest owner is `scripts/verify-local.mjs`. It retains the documentation-only optimization from #730 through the existing `scripts/ci-change-scope.mjs` owner: only root `AGENTS.md` and Markdown under `docs/` qualify. Eligibility comes from the proven current base-to-integration checkout diff, with ancestry and checkout agreement and both paths of renames/deletions; no user flag selects it. Unknown/empty/unavailable metadata, divergent history and every mixed or out-of-allowlist change select its complete plan. There is no API reuse within this verifier. Commands remain owned by the existing packages and verification scripts.

For a proven documentation-only change, the verifier selects the existing simple doctor, format, lint, strict types, complete script suite and documentation API contracts. The manifest retains all sixteen families; the ten heavy families and their Railway/DB/browser prerequisites are explicitly `not_required` with the canonical source-derived reason, never passed or arbitrarily skipped. The report shows the scope, reason and exact argv, and validation recalculates eligibility from the real source/base/integration inputs before accepting those results. For any other change, the verifier selects its complete command plan below.

## Complete command plan

For full-scope changes, the API parallel and serial commands together cover the complete API suite. The runner records a fixed local execution profile in its exact argv: the API parallel family uses `--maxWorkers=1`, web unit uses `--maxWorkers=2`, and browser uses `--workers=2`; the canonical Node script suite uses `--test-concurrency=2` to bound test-file concurrency. Both API parallel and API serial add `--testTimeout=15000`, changing only their inherited test timeout from the canonical API's implicit 5000 ms default to a fixed 15000 ms local allowance. Explicit test or suite timeouts still take precedence; hook and internal-command deadlines, all selected tests/assertions, and all browser/acceptance budgets remain unchanged. Both canonical local API families also use Vitest's public `--bail=1`: after the first registered failure, later cases do not execute their `beforeEach` or body and are never counted as passed. Fail-fast cannot abort an already-running asynchronous body or its `afterEach`/`afterAll` cleanup; it does not diagnose or fix the underlying latency investigated in #616. API serial and acceptance retain their existing serial policies. The canonical package scripts, API configuration and Actions commands remain unchanged. A local pass does not prove success within the canonical 5000 ms default or establish a business response SLA. This reversible local execution choice does not claim matching GitHub runner hardware. Browser and real-PostgreSQL acceptance run both existing desktop/narrow projects; the acceptance failure-evidence probe remains mandatory. Build, Railway configuration tests/types and the actual production packaging smoke remain required. Missing Docker/images, database configuration, browser or dependencies produce failed/incomplete evidence, never a successful skip.

The plan also records finite process safety caps for the aggregated local commands: API parallel and browser each use 270 minutes (2 × 3 × the workflow's 45-minute shard budget), acceptance uses 180 minutes (2 × 2 × 45), and other families use 45 minutes. The factor of two is a conservative local margin, not a measured runtime claim. These caps terminate an entire child process and its descendants; they are separate from the fixed local API test default described above. The validator recomputes both process caps and literal argv, including the API `--testTimeout=15000` and `--bail=1` values and families marked `not_required`. Before running, prepare application dependencies with the normal frozen-lockfile setup; for full-scope changes, separately run `pnpm --dir .railway install --frozen-lockfile`. The verifier checks installed Railway/TypeScript versions against that tracked manifest, whose separate lock is included in input hashes; the runner does not install or acquire substitutes.

Browser and acceptance use the closed local startup helper `scripts/verify-local-browser.mjs`, while the Actions commands and canonical Playwright configurations remain unchanged. The helper always removes only its listed generated build outputs and performs the real required builds before launching Playwright: web `pnpm build --mode local-demo` in `apps/web`, preceded for acceptance by `pnpm --filter @prisma-prim/api build` at the root. It records their exact public environment, inputs, dependency/tool identities, output path sets and byte hashes, argv, UTC and exits in `local-browser/<family>/manifest.json`. An external temporary configuration imports the registered configuration and preserves its test selection, projects, global setup, use/expect and scenario budgets, reanchoring relative paths to `apps/web`. Its only startup change is a fresh-build guard followed by the original preview command, with a finite 180-second local guard/preview startup window; builds run outside that window but inside the unchanged family process cap. Guard/config/input/output drift refuses preview. No older lot, arbitrary command or skip option qualifies. Child output logs remain private execution evidence until the operator selects and sanitizes publication artifacts. Acceptance helper failure or process expiration still runs the independent existing evidence probe, retaining acceptance failure and partial results; external interruption cancels work and cleans owned descendants. The probe has neither a server nor a database setup, and cannot turn a failed acceptance run into success.

## Run and validate

1. Fetch the current base and record the proposed source commit. Create an isolated disposable checkout of their actual merge, with no untracked source or tracked edits. For example, from the issue checkout: `git fetch origin main`, `git worktree add --detach /tmp/issue-integration origin/main`, then in that worktree `git merge --no-edit SOURCE_SHA`. Resolve conflicts on the issue branch and start again rather than inventing an uncommitted integration. When the base is an ancestor, the source checkout itself already has the integration tree. Provide the installed dependencies and, for full-scope changes, the normal safe isolated PostgreSQL URLs to the integration checkout; use the existing managed-PostgreSQL lifecycle when appropriate.
2. In that clean integration checkout, run `node scripts/verify-local.mjs run --source SOURCE_SHA --base origin/main --output /tmp/issue-evidence-UNIQUE`. Use a fresh external output directory. The manifest records source/base/checkout SHAs, the exact merge tree, every tracked input's hash (including manifests, locks and configuration), allowlisted tool/DB/browser versions, effective environment policy and overrides, literal argv, UTC timing, each family exit/result, and artifact hashes. Database credentials/URLs and unrestricted environment dumps are excluded. Each executed family retains a structured `executionOutcome`: `completed` requires a zero exit without a signal; `command_failed` records a nonzero exit with `cause: undetermined`; `process_timeout`, `external_interruption`, `launch_failure` (with its Node error code) and `child_signal` identify incomplete execution. The compact report labels incomplete execution separately from a command failure. A nonzero exit may include an assertion failure, a Vitest test/hook timeout or another runner error; neither elapsed duration nor human log matching determines that cause. Every failed or incomplete outcome remains non-qualifying, and validation requires the exact successful outcome for every required family. Unexecuted and `not_required` families retain a null outcome; existing evidence is never relabelled as passed. Required failures leave later families explicitly unexecuted. `contract-test` reports are synthetic runner-contract tests, not execution of the application suites.
3. Before claiming a report still applies, refresh `origin/main`, ensure the source still matches, then run `node scripts/verify-local.mjs validate --output /tmp/issue-evidence-UNIQUE` in the same integration checkout. Changed source, base, integration, input bytes, missing/failed families or altered artifacts invalidate that report. Repeat a run only when the diagnostic need and approved cost justify it.
4. When publishing local evidence, attach the compact `report.md` and machine-readable `manifest.json` with exact configuration, actual artifact links and checksums in the PR. Retrieve/check the uploaded assets before claiming publication; a local path or digest alone is insufficient. Keep failed/incomplete reports honest and separate from successful runs.

The runner deliberately executes a small allowlist of inherited runtime/path/proxy/CA/database settings and fixed PostgreSQL/CI requirements; other environment overrides are excluded. Tracked configuration hashes and literal commands provide the remaining effective configuration. Credentials must be provided privately to the reproduction environment. Local evidence is self-reported execution, not independent GitHub runner attestation; never create a GitHub success status from it.

## Publishing evidence

For bounded binary publication without source-history artifacts, use a GitHub prerelease per PR, named/tagged `local-evidence-pr-N`, targeted at the tested source commit. Upload a reviewed archive containing the sanitized logs and synthetic `browser-evidence/`, plus the report and manifest; include the source SHA in immutable asset names, never overwrite a different run, and link the actual release/asset URLs in the PR. Use `gh release create`/`gh release upload` only under the session's publication authorization. Split archives below GitHub's per-asset limit when necessary. Keep at most the current passing run and its immediately preceding failed run for each open PR; after merge retain the final compact manifest/report and linked evidence for 14 days, then delete bulky archives. Keep evidence still needed by an open review. This uses existing GitHub storage, creates no new hosting service, and never commits binary evidence to normal product history. Review logs, screenshots and traces for secrets or real data before upload; automated text redaction does not certify binary content.

If release-asset publication is unavailable, the session may create a unique temporary orphan evidence ref named `local-evidence/pr-N/SOURCE-RUN`, with a parentless initial commit containing only reviewed synthetic evidence. Never overwrite a different run or merge, rebase or cherry-pick that evidence into product/source branches. Limit the total stored file bytes per run to 20 MiB and each blob to 5 MiB, splitting archives if needed; these are conservative repository limits. Publish the compact report/manifest and immutable evidence commit links in the PR. A publication index must bind the run, source/base/integration, paths, sizes and SHA-256 values, distinguishing selected or sanitized copies from the complete originals retained locally. Required proof that cannot fit remains blocked. Use only authorized GitHub Git endpoints, retrieve the published blobs and verify their SHA-256 values before claiming publication; never bypass a denied destination. Apply the same retention limits above and delete only the owned evidence refs after their retention period. Orphan refs remain in this repository and may enlarge normal clones; deleting a ref does not guarantee physical erasure of GitHub's objects. Keep this fallback small and temporary, and never publish secrets or real data through it.

## GitHub CI artifacts

This procedure changes none of the CI workflow's commands, failure aggregation or full browser artifacts. Retrieve GitHub browser evidence under `browser-evidence-pr-RUN_ID`; the five shard artifacts remain recoverable individually if aggregation fails.
